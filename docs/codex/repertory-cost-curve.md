# 仓库分段费用与电力长线复核（P40，2026-09-24）

文档目标是让母本的仓容成长、付费门槛与我方实际产能一起形成可达的时代曲线；当前代码在P39前一直把带`storageCostStep:5`的仓库写成`基价×(1+当前等级/5)`。母本解包版`210(1)_unpacked/_analysis/deob_main.js`的`addRepertoryLv`（约1488609）对全部仓库使用如下按当前等级`L`的单次费用；配置实体的`Need`是各资源基价`B`：

| 当前等级L | 下一次升级的每项资源费 | 铁仓／钢仓 B=200 示例 |
|---|---|---:|
| 0–9 | `B×(1+L/5)` | L=9：560 |
| 10–299 | `B×(1+9/5+(L−9)×2/5)` | L=10：640；L=299：23760 |
| 300–599 | `B×(1+9/5+(L−9)×3/5)` | L=300：35480；L=599：71360 |
| 600及以上 | `B×(1+9/5+(L−9)×4/5)` | L=600：95120；L=999：158960 |

这里在300／600级发生**费用跳升**，并非让前段斜率累计后平滑衔接。`config.js`集中记录断点，`math.js:upCost`按同一函数计算机械期各专仓及新档对齐模式的木石仓；仓库首建费用、旧档`storageMode=legacy`的原仓库价格、其它建筑费用、建筑工期和容量公式均不动。真实`buildAct`读取这个价格，扣费一次、写档失败恢复原库存和建筑状态。旧主档`rts_save`仍为v21，不新增字段，也不裁剪升级前已持有的资源或高等级建筑。

两条新路线的钢容量仍至少100万、知识容量5001920。铁仓300级比当前不额外升铁仓路线快563935在线秒≈156.65小时，但多150次建造；仅在这两条固定路线内成立。它们在第1134782秒到冶钢厂30级、第1942881秒到储存精通100级、第2259264秒到知识容量500万；后段钢仓升费是两线时长差的主要因素。P39的688／636小时是**旧费用历史结果**，不能继续描述成当前版本的耗时。P39的600／900级分支尚未在新费用下复跑，当前不对它们重新排序。

这次是明确的费用忠实性修正，不是难度曲线完成。当前双线仍能到电力，但在线时长显著增加；需要继续核对母本其它产能、仓容、军备和操作减负层，再按新费用重算完整十时代。所有探针时间均为游戏在线tick秒，固定既有战斗随机脚本，真实逐笔生产／研究／建造／招募；没有注入资源、人口、科技、建筑、兵力或胜利。实际点击、建筑动画、离线、不同岗位和战斗胜率未计。机械期仍使用仓储、冶钢等工造名称；神魔西幻名留给后段。
