## 本批开工前必须定的语义

1. **矿石库存身份**：我方 `stone` 同时承担建筑石料与采矿来源，母本的「矿」是否映射为它，须在设计中明写。如果沿用 `stone`，冶炼会与建筑争同一库存，需重算产率、仓容及首个可支付费用；如果新增 `ore`，它同煤一样需要完整的存档、岗位、建筑、容量和 UI 链。不能把 `stone` 改名后让旧档含义悄然变化。
2. **配方与效率**：当前 `prodRate()` 用工人数×每人基础产率×建筑 Buff，而 `productionSecond()` 的原料费按工人数计，Buff 不增加原料费。母本按每次加工耗料。要明定本地每秒配方、Buff 对输入/输出的作用、满仓只生产可存部分时是否按比例扣料；不直接把母本「2秒产1铁」误记为「每秒产1铁」。研究费、建筑费和生产费都须标秒或单次。
3. **旧金属进度**：已有存档可拥有铜、铁、矿井、冶炼厂、`sci_copper`/`sci_iron` 与已分配金属工。把铁的铜耗换成矿/煤后，这些玩家可能立刻断料。选择明确的迁移过渡（例如保留旧配方直到煤链完工，或给已研究者可抵达煤链的既得解锁），保留原库存和工人分配；不得静默撤销科技、裁剪资源或将断供称为难度曲线验证。
4. **真实消耗端**：当前发展研究只扣科技点/战功，建造与训练只扣木/石/粮；铜、铁目前主要是库存与产线，缺主线单笔材料门。若本批要证明「青铜→铁器」成长闭环，须给研究、建造或军备一个有证据的铜/铁用途，并验证「采矿/采煤→冶铜/冶铁→支付→解锁」；否则本批只能称为原料链铺设。

## 最小有意义的回归路径

下列用例应通过现有 `tests/progression/harness.js` 调**真实** `researchScience()`、`buildAct()`、`setPopAlloc()`、`tick()`、`offlineAdvanceSec()`、`save()`/`loadSaveAndApply()`，不另写一套资源公式：

1. **新档从零到铁**：不注入金属资源，在线产科技→依次研究煤/铜/铁前置→建煤井及金属加工建筑→派矿/煤/铜/铁工→原料与成品均有正确正向流量→支付一次真实青铜/铁器材料门；同时记录所需聚落上限、粮工、单笔仓容与真实经过秒数。如果矿石独立，先加矿工全链；若 `stone` 兼矿，测试施工与冶炼的同库存竞争。
2. **缺料/满仓/离线**：煤=0 或矿=0 时铜铁停产且库存不负；恰好够一秒原料时只扣一次；成品满仓不烧原料，历史超限成品不被削；过渡存档若已分配煤工，煤井在离线第 N 秒完工后才可产煤，新玩家未派工则完工后仍不产；矿/煤耗尽后可停工并在来源恢复后继续；在线与离线同倍率逐秒结果一致，断粮一秒回退训练及建设，重复离线不再结算。
3. **存档与事务**：legacy/v2/v3/v4 的煤/矿 0 值候选迁移、`rts_save_premigration` 原文保留、旧铜/铁/科技/分配不缩水；新版本往返和导入/恢复；未来版本及非法/未知资源保护；迁移前副本、轮转备份、主档写入三处故障各自不损主档；材料研究、市场和建造扣费失败不虚报成功、不重复扣除。
4. **边界共用路径**：给一个煤/金属库存高于木仓但在其专属容量内的档，触发驻军胜利 0 金属奖励，验证库存逐键完全保留；再验证驻军战败损失规则与远征的新增材料奖励按单资源仓容结算。若新兵消耗金属，确认训练→编入远征/驻军→tier 更替/遣散返还无遗漏。
5. **浏览器冒烟**：通过 `index.html` 真正加载顺序在 360×800 和 400px 宽度检查顶栏、建筑卡、科技按钮、岗位增减、保存刷新后的新资源/人口一致；Node VM 的 DOM 替身不等于真实界面验证。
