## 先定资源身份：推荐沿用 `stone`

母本「矿」是独立资源：矿工 `2/秒`，铜工每秒吃矿2+煤2产铜1，铁工每2秒吃矿4+煤2产铁1；煤工 `1/秒`。我方 `stone` 已由石料工 `2/秒` 生产，同时支付建筑、军备和市场费用（`config.js:16-23,269-313,375-386`）。**推荐本切片内部沿用 `stone` 作为可冶炼矿石兼建材，不另造 `ore` 键**；UI 名称可写“石料／矿石”，策划文档明确共用库存。旧档石料数量原样保留。这是我方简化，不是母本拥有同一资源的证据。

若坚持建筑石料与矿石分离，必须同时新增 `res.ore`、`popAlloc.ore`、矿工、矿仓、显示、奖励语义和 v5 迁移，重新定起始库存、首笔矿费、人口预算；这应成为另一张任务单，不能在实施中途只改文案或偷偷把旧 `stone` 库存兑换成新矿。当前选择让木石建筑和冶炼争同一份 `stone`，必须用实际行动回放证明不会卡死。此决定是开工前唯一会改变本切片数据结构的分岔；下文均按推荐方案。

## 建议落地的规则

| 项目 | 新煤链档的候选规则 | 与母本／现状的边界 |
|---|---|---|
| 岗位与研究 | `sci_prospect → sci_coal → sci_copper → sci_metal → sci_iron`；保留城镇化与铁科技的现有分叉及已研究 ID。煤工研究煤后开放，铜／铁工分别研究铜／铁后开放；工坊只加产率，建造不再是新煤链档派工的前置。 | 母本煤工 450007、铜工 450009、铁工 450011 由研究开放，煤井／冶铜厂／冶铁厂是后续增效侧支；我方插在现有八节点中是适配，不能称原样复制。旧配方档继续按现有建筑门派工。 |
| 生产（资源／在线秒／人） | 煤 `+1`；铜 `+1`，消耗 `stone 2 + coal 2`；铁 `+0.5`，消耗 `stone 2 + coal 1`，**不吃铜**。先结算石与煤，再结算铜、铁。缺任一原料时当秒该工种停产且不扣原料；成品满仓时按可存比例扣料。离线系数同时乘产出与原料。 | 母本铁是两秒一批；我方 `productionSecond()` 是秒级连续数值，`0.5/秒` 是等效适配，不能声称逐事件时序相同。现状铜无输入、铁每工每秒耗铜3（`config.js:20-21`）。 |
| 专属仓 | 新煤链档建议煤／铜／铁各基础容量 **600**，各自专属仓每完成一级 `+200`；通用木石粮仓和增效工坊不扩这三种库存。煤仓／铜仓／铁仓分别由相应研究开放，首级只花木石粮且低于通用仓现有容量；升级沿用仓库线性成本和自身等级上限。 | `600` 来自母本资源基础 Max，但 `+200` 和建仓费用需在我方曲线中复核。母本的多个仓库有交叉扩容，不能声称我方三个专仓与其逐项相同。当前我方铜、铁启用扩容时为 `8000+2000×矿井Lv`、`6000+1600×冶炼厂Lv`（`config.js:403-407`）；**旧配方档继续保留这套容量**。 |
| 工坊 | 煤井新增为煤岗位增效建筑；现有矿井和冶炼厂继续给铜、铁增效，均保留现有建筑 ID。工坊、专仓可从对应研究后建造，首级费采用木／石／粮，避免这批还要扩展 `buildAct()` 三资源付款协议。 | 母本工坊研究比岗位研究晚。本切片只保留“岗位先于增效”的依赖形状，工坊侧支研究的精确节点留待十时代账本统一安排。 |
| 人口 | 不新增关卡人口奖励。新链第一笔铜可用石1、煤2、铜1占4人短时启动；持续运转还需粮／科研／木工。铁与铸币并行的**测算起点**为实际／容量18：石3、煤4、铜1、铁1、木1、学者1、粮2、铸币1，共14岗，留4人调岗。 | 该预算来自[人口方案](population-growth-proposal.md)，无建筑加成、无军粮时石净约+2、煤净约+1、粮净约+1.7／秒。它是待真实函数验证的目标，旧“铁耗铜”配方下的14人候选不再适用。 |

**本切片只使上游生产与研究门闭合，不另加铜／铁研究材料费。**母本此段的发展研究以知识付款，铜、铁最早的明确消费之一在青铜刀盾兵／铁器长枪兵各100金属（母本账本 @1097885/@1098357）；把铜700或铁700强塞进现有 `sci_iron`／`sci_city` 会制造一条未经用户裁决的新费用曲线。下一张军备任务必须给铜／铁真实消耗端，并复核训练、退款、远征与驻军；在此之前，本切片验收只能称“矿煤生产链可达”，不能称青铜／铁器完整成长闭环。专仓本批通过容量和后续付款能力验收，不必为了强迫建仓虚设循环费用。

## v5 旧档迁移与切换

`sourceVersion<5` 时先按现有 v0→v4 规则填充，再在独立候选对象补 `res.coal=0`、`popAlloc.coal=0` 和模式；保留已研究 ID、建筑、人口、全部铜铁与超仓库存。若候选已有铜／铁库存或岗位、已研究铜及其后继科技，或矿井／冶炼厂正在建造或曾建成，标 `metalRecipeMode='legacy'`；没有任何金属进度的旧档标 `coal`。这个判定须只读迁移候选，不在验档失败时碰 S。`v5` 必须明确含三个新字段，合法0保留，缺字段或模式不在枚举内判坏档；`v6+` 拒载。版本变化本身也要触发迁移写回，不能只以“补了几个键”判断是否迁移。

`legacy` 模式保留旧铜无料、铁耗铜3／工／秒、铜铁建筑派工门和原有效仓容；已研究节点不追加煤前置，不追缴新费用。UI 明示“旧配方”，允许研究煤、配置煤工与专仓。给一次性“切换煤链”动作：至少研究煤，列出切换后的铜铁配方、容量及当前库存是否高于新容量；玩家主动切换，保存成功后生效，不自动切、不可反复双向切换。切换不裁剪已有库存；若高于新容量，后续产出自然暂停到消耗／扩仓后恢复。切换失败则整个模式和库存保持旧值。旧代码回滚会把 v5 识别为未来档，恢复需用导出的旧档或 `rts_save_premigration`，不能说“旧版会忽略新字段”。

## 最少可达性验收（新增测试必须调用真实实现）

1. **零战斗从 0/4 到铜铁**：新档只用起始木石粮300、地契30，经学院、人口增长、现有村庄扩建／市场购契、煤研究、煤工、铜研究、铜工到 `铜>0`；再经现有冶金／铁研究到 `铁>0`。不直接给煤铜铁，不把第372秒市场样本当保证。输出每步时间、实际／容量人口、已分工、净粮、石煤净流、研究单笔费用和上限；铁与铸币并行再以18人口预算验证，未达到则调方案而非跳过。短时上线／离线口径另跑一条。
2. **一秒原料与仓**：新模式石1工+煤2工+铜1工，在允许工作且非满仓时一秒石 `+2−2=0`、煤 `+2−2=0`、铜 `+1`；石1工+煤1工+铁1工时石 `+2−2=0`、煤 `+1−1=0`、铁 `+0.5`，铜完全不动。缺任一料、不足一整秒的原料、满成品仓、仓建造／升级中、旧档超仓均不负数、不凭空产出或裁剪。离线0.6系数验证输入与输出同倍率，重复结算不再发奖。
3. **容量墙**：新模式煤／铜／铁默认各600，专仓完成1级后各自独立+200，木石粮通用仓与矿井／冶炼厂不扩这三者；旧模式铜铁仍使用旧上限。建仓首费小于付款时木石粮各自上限，不形成“先有仓才能付首仓”的死锁。
4. **兼容与失败路径**：v0/v2/v3/v4 迁移、已有铜铁工与研究、合法0与历史超仓、v5往返／导入／恢复、v6未来档；迁移前副本、备份、主档写失败分别验证主档和 S 不被污染。旧模式原产率／原料保持；切换煤链失败不改变模式。驻军零奖励及远征领奖不裁剪现有煤铁。运行现有 `tests/ie001/run.js` 和 progression 相关套件，再做真实浏览器 360／400px 冒烟。

完成本切片后还需一张铜铁消费与青铜／铁器军备任务单，以及四策略实际时长推演；本稿没有替它们验收，也没有改动游戏代码或玩家存档。
