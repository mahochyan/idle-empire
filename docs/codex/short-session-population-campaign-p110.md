# 短时会话延伸到军备、战斗与补兵（P110，2026-09-25）

- 对应权威设计：[《策划文档.md》§8.4、§8.6、§8.9](../../策划文档.md)
- 探针：[全早期战役短时会话P110](../../tools/verify/probe-short-session-population-campaign-p110.js)；会话计时扩展在[首战与补兵探针P102](../../tools/verify/probe-population-first-clear-replenish-p102.js)。
- 原始结果：[P110逐分支数据](reports/data/p110-short-session-population-campaign.json)。
- 存档：P101通过真实`save()`生成两个18人口零胜场路线终档；P102由`loadSaveAndApply()`读取。数据只在隔离开发harness中流转，不读写玩家浏览器存档。

## 方法和会话时钟

连续在线和短时路线均从新档运行P101，输出其实际终档并交给P102。短时路线沿用P101累计时钟：P102军备准备开始时为4188在线秒、172800离线秒；profile为每600在线秒后`save()`并调用实际`settleOffline()`结算28800秒。由于下一个边界在4200秒，军备准备先运行至该边界，实存后离线8小时，再继续建造、训练和首战准备。

战斗计时器按当前`CFG.battleStepDelay`、`CFG.battleRoundDelay`和`S.battleSpeed`的实际回调延迟排列，同时按`CFG.tickMs`调用真实`tick()`。这保留当前代码语义：战斗中的tick递增游戏时钟，但在`S.battleActive`时不进行建筑、资源生产或训练队列处理；离线只在战斗结束、补给操作后的实际会话边界结算。战斗固定随机值0.5，检验现行奖励、第三关后+6地契（金属岗位）和+6地契（稳粮岗位）三条分支，以及每胜0／60／180／600秒补兵窗口。

## 结果

首战准备跨4200秒边界触发一次离线结算。离线开始前为18／18人口／容量，已完成的步兵与猎人数量在准备阶段尚未训练；离线后真实仓储结算，再经主动tick完成训练。战役入口为tick 206011、18／18人口／容量、步兵15／猎人13／青铜刀盾兵8。P102准备的累计在线时钟为4411秒、累计离线201600秒。

|---:|---|---:|---:|---:|
| 0秒 | 三分支均胜5场，第6关失败 | 4502 | 201600 | 0 |
| 60秒 | 三分支均通过前六关 | 4743–4744 | 201600 | 0 |
| 180秒 | 三分支均通过前六关 | 5222 | 230400 | 1 |
| 600秒 | 三分支均通过前六关 | 6902 | 316800 | 4 |

三条奖励／岗位分支在每个等待档的胜负结果相同。原始数据对第3关及之后的战斗保存了回调时长；第1、2关同样由定时器和主tick推进，但当前战役摘要不按关输出其单关耗时，因此不能把已列回调时长误读成六关总战斗时长。自动化动作本身不计入操作耗时。连续在线对照仍为0秒／胜5胜后败第6，60秒及以上通过。故当前证据下，短时用户即使军备阶段触发8小时离线，也没有改变本固定编成的首六关门槛；额外补兵等待才决定0秒档是否能连续通过。

## 限制与含义

1. 这是单一早期18人口路线、一个固定随机值和三种敏感度分支，不是均衡／军事策略比较，更不能外推真实玩家胜率或实际会话长度。
2. 战斗回调采用虚拟定时器驱动实际战斗函数；不含浏览器渲染、设备调度、玩家点按时间。这个计时复现了本项目当前配置的战斗延迟与游戏tick，不代表真实设备上的精确秒表值。
3. 8小时离线资源受实际仓容、岗位与动态结算限制；结果不应简化为“离线8小时就够补满”，每段原始数据记录了实入资源、兵力、队列及离线窗口。
4. 本批仅增加开发探针可选的时钟和计时器路径，不改玩家运行代码、CFG、奖励、存档格式或美术。既有P102无参数流程和P109短时人口路线均保留并复核。
