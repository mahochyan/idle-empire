# P230｜100关高难主线的实际解锁门复核

**按最新分工：固定100关保留高难主线，另一套副本承担《放置时代》式区域与材料发展。**当前不是把100关降为可选支线，因此不建议现在整体迁走第5／20／40关的兵种研究和训练门。需要先证明每个门**可以用门前军力实付打过**，再让发展线提供可持续的资源、人口和军备补给。源码目前也没有“研究完全部科技才可挑战第100关”的动作条件；高难与全科技需求尚不能仅凭策划文字当作已实现。

## 动作层逐项核对

| 门与实际调用 | 当前真正生效的条件 | 主线/发展线接缝 |
| --- | --- | --- |
| 兵种研究 `technology.js:101–115,143–218` | `upgradeUnit()` 和 `unlockUnitRoot()` 都调用 `checkTierLevel()`：目标T1要已胜第5关，T2要第20关，T3要第40关，T4+映射第65关；还要前置已研究、对应训练建筑的 tier、科技点/战功/精魄/资源，成功后保存 `S.upgradedUnits`。`trainLockReason()` 与 `train()`又检查研究、建造、tier、队列。 | **保留**第5/20/40关作为高难主线军备里程碑；发展区的材料与资源科技可并行帮助支付和补兵。不能只放开科技页按钮，而漏掉建筑与训练动作。当前玩家单位最高T3，`checkTierLevel(4)=65`暂时没有T4兵种调用。 |
| 训练建筑升阶 `config.js:347–373`、`math.js:2202–2257` | 步/弓营地初始T0，实际依次由第5／20／40／65关升到T1–T4；`buildTierUpgradeAct()`调用 `tierUpgradeLockReason()`再扣费保存。骑兵场/法师塔建成初始T1，正常新档的下一步按数组索引1起，分别需第20／40关；法师塔再升T4需第65关，骑兵场无T4条目。配置中两者 `tierUpgrade[0].needBossId=5`对正常初始T1档并非当前动作门；**历史 `tier=0` 旧档仍可能走该项**。 | **保留**有效关门并核对门前阵容；第65关只解建筑T4、未解新T4单位，不能宣称它已构成完整科技成长。旧建筑 `tier` 不得因整理索引而强制归一。 |
| 阵位 `math.js:523–547,2542–2640,2740–2758,3816–3831` | `rowSlots()`按前排第5/20/35关、中排第10/25/40关、后排第15/30/45关分别由1逐格到4；`openFormModal()`、`confirmForm()`、恢复上次编队与下一关重编队均调用。相同弹窗入口也供 **驻军** 使用，故这些主线成绩目前同时影响两种阵位。 | **保留**既有已胜关与已开放格；发展线必须按当时可用格位校准，不把尚未打开的格位当作前置战力。若将来需要并行来源，应集中改 `rowSlots()` 的统一判定，同时测远征、驻军、旧阵容回填。 |
| 骑兵/法师入口 `config.js:361–373`、`math.js:437–488,2169–2185` | `stable.needBoss=1`、`mage_tower.needBoss=4`均由 `buildAct()`和 `trainLockReason()`动作重验；Boss数由 `CFG.enemies` 中已记录在 `S.defeated` 的不同Boss计算。按自然顺序首四个为10/20/30/40关，骑兵场通常过第10关、法师塔通常过第40关才可建；**动作只数Boss，不指定这些ID**。`mageOk()`虽写“2 Boss”，仅被弹窗的 `k==='mage'` 过滤调用；`CFG.units`无 `mage` 键，实际为 `mage_t1` 等，且 `confirmForm()`不检查 `mageOk()`，故它**不是现行有效法师编队门**。 | 法师在第29/39关已成为敌人，但按自然顺序本方要过第40关才可训法师；这是主题/战术职责错位，已有非本方新法师的实付路线能过第29、40关，不等于全面自锁。若设计要求玩家用法师应对第29关，应单独调整**塔建造和训练动作**的4 Boss门，不能只改弹窗。 |

| 历史城镇字段与首胜 `config.js:60–71`、`math.js:216–237,684,736,1068,3746–3767` | `CFG.town[*].needBossId`、`townUpgradeNeedBossId()`保留历史定义，但 `townCanUpgrade()`固定返回 `false`；自然出生、聚落扩容走粮食、地契和资源科技，**无此Boss门**。然而旧 `S.townLv`仍影响部分建筑等级上限、驻军模板以及历史待完成 `townUpgrade`结算。`S.defeated`还是100关记录、第3关拓居令一次首胜判定及Boss计数来源。 | 不挪用或改号现有1–100关ID；保留已胜、首胜资源、旧城镇等级/未完成升级。新区域必须有独立进度与首次/复刷判定，不得重发旧首胜。 |

100关选择本身也没有逐关动作锁：`selEnemy(idx)`直接设索引，`openBattle()`只检查已选择、已编队和存档保护，没有要求前一关胜利；界面默认索引用 `S.defeated.length`。因此**当前不能保证玩家按1→100顺序通关，也没有“全科技完成才可打100”的显式锁**。若最终设计要通过强度而非硬锁体现“解锁所有科技后才能打完”，需用真实终盘档验证，而不是把直接选关误称为顺序门。

## 最小实施与验收顺序

1. 先冻结主线1–100关ID、`S.defeated`、第3关首胜和已有 `S.upgradedUnits`／`S.buildings.*.tier`／兵池、编队与精魄；发展线使用独立区域键及 `S.killValues` 或新命名进度，按存档版本补默认值、验证、迁移、备份与回退。**本批不改代码或存档。**
2. 用同一付费旧/新档对第5／20／40关做“门前可打→获胜→建筑升阶付款→研究一次扣费→真实训练→下一关可编队”的闭环；第65关先核实T4实际单位/用途与门前战力，再决定保留还是重定位该门。现有 [P170](early-t1-handoff-p170.md)、[P186](live-l20-boss-p186.md)、[P206](live-l40-l41-handoff-p206.md)分别给出第5后T1、第20与第40的部分真档可达证据，**不覆盖第65/100关或全策略**。
3. 发展线先给出门前材料、住房、粮和训练费的实付来源，分别试“未过主线门”“刚过门”“旧档早已过门”三态。仅当真实同档证明发展线被主线门反向卡死时，再为**那一个门**设计发展里程碑并行判定，集中接入 `checkTierLevel()`／`tierUpgradeLockReason()`／`rowSlots()`／建塔训练门的相关动作；不要重写 `S.defeated`、静默发Boss成绩或只改UI文案。这样保留高难主线荣誉，又避免发展闭环自锁。
4. 验证旧档原文加载后关卡、研究、建筑tier、兵力、阵位、资源、待建队列全不缩水；新发展记录不碰主线首胜；异常/未来档仍阻止自动保存；保存失败回滚一次扣费与奖励。追加远征/驻军阵位、特殊区域重战和浏览器/Android入口验证。第100关的“全科技才过”须另用满科技与缺关键科技的可付终盘对照检验，目前不能判定。
