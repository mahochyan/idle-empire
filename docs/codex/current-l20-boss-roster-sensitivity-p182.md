# P182：第20关统领敌阵隔离敏感度（2026-09-26）

> 历史基线：表中的“现行`[1,1,1]`”指P186调整前配置；`[8,6,4]`现已接入玩家关卡，见[P186](live-l20-boss-p186.md)。本探针的输入哈希属于调整前快照。

## 起点与口径

[探针](../../tools/verify/probe-current-l20-boss-roster-p182.js)读取[P180四份第19关真实战后档](reports/data/p180-current-l18-l20-cavalry.json)中的`l19ContinuationSave`，逐份校验存档SHA与已击败1—19关，再用真实训练队列和逐秒`tick()`补回青铜刀盾兵15／侍从骑士15／游侠13。补兵耗时、产出、粮低位及战前状态逐项等于P180原记录。四份战前档再次保存重载后，各自派生10个隔离VM；唯一试验变量是内存中的`CFG.enemies[19].units`，三兵系各沿前／中／后三排使用同一组人数。第20关名称、Boss倍率、掉落和奖励、玩家源文件及玩家存档均未改变。

每个VM调用真实编队、`initBattleState()`、固定同源随机流的异步`openBattle()`回调、结算与保存重载。现行`[1,1,1]`敌阵还逐项断言与P180的四支战果、回合、入场、战损、实入账和战后状态一致，作为敏感度基线。所有40场均由43名实兵（15青铜／15骑兵／13游侠）入场；关卡准备仍是P180的在线补兵，不为候选阵容再注入资源或士兵。

当前第19关为78 HP、初始`ATK×出手人数`702、四支骑兵线损22—34人；现行第20关只有9 HP和105，确实比关前轻。`[8,6,4]`在本样本增加压力但四支仍胜；`[10,7,4]`把四支胜利推到4—5回合、战损24—33；`[12,9,5]`四支均全灭。因此`[8,6,4]`与`[10,7,4]`适合下一步拿P181的有奖游侠30／36真实续档追加复核，**它们不是最终推荐配置**。本批未测63与78 HP之间的转折，更不能凭两个随机种子估计玩家胜率。

所有假设保留第20关名义奖励木6000／石4500／粮4080、战功25和精魄概率。胜利时实入账受相同战前仓库状态限制：木0、石6、粮约2995—3000，战功25；失败时资源、战功和精魄均为0。各候选的具体随机精魄、兵种战损、编队、回调次数与战后重载状态在[原始JSON](reports/data/p182-current-l20-boss-roster.json)中，不以固定随机掉落推断概率。

## 公式联动、续档接口与验证

现行`math.js`的`combatSurvivors()`从兵团HP换算幸存人数，`combatAttackMass()`以幸存人数作为普通兵团出手规模；远征`calcDmg()`与驻军`calcGarrisonDmg()`均调用它。故本批改变第20关`units`数量会**同时提高生命与攻击输出**，不能把横轴理解为只加血。第20关属于远征配置，驻军没有读取这份关卡敌阵；本批没有改动共享公式。候选仍为30回合上限、9团，Boss攻击／防御倍率不变。

P182原始JSON的`scope.rosters`保存可复用候选列表，`profiles[*].l19SaveSha256`指向P180的四份原始`l19ContinuationSave`。探针作为模块导出`prepareFromL19Save(save, recoveryFn)`和`runVariant(preparedSave, seed, roster, form, expectedDeployed)`：前者调用真实重载／补兵／战前保存，后者只在隔离VM覆盖第20关`units`，然后真实结算并重载；自有路线可传入自身的补兵函数、编队函数和实入场预期。这提供P181游侠档复核入口，不需改`levels.js`。
