# P353：放置时代训练队列与自动补兵口径

2026-09-29；当前 `master`，`HEAD=f85e1c8624de8c9e17f7724373e65899d1085cdf`。本项只读核查参考游戏反混淆源码和本项目现行实现，没有改玩家规则、存档或 UI。下面的参考源码位置是 `210(1)_unpacked/_analysis/deob_main.js` 的 JavaScript UTF-16 字符索引，不是行号。

| 行为 | 放置时代源码 | 我方现状 |
|---|---|---|
| 训练下单 | `addAmryAmount` 约 1,579,285：按 `Need × 数量` 验证库存，成功时一次扣足并增加 `ArmyList[id][1]` 待训数；现役与待训共同受全军上限约束。 | `math.js` 的 `train()` 只入队和保存；`processQueue()` 到产出时才扣每名材料，缺料暂停。 |
| 取消待训 | `reduceAmryAmount` 约 1,582,379：取消尚未训练的订单，按原材料全额返还，受当前仓容限制；已成兵的 `dismissArmy` 不返材料。 | `dismissN()` 取消未产队列不退款；遣散后备兵仅返一半木／石／粮，不返金属。 |
| 离线训练 | `armyOffline` 约 1,418,367：以离线秒数和兵种间隔把**已付费**待训转现役，不在离线期间采购材料。`getOfflineResource` 约 1,404,157 先处理既有训练再结算其它离线收益。 | `offlineAdvanceSec()` 每秒调用 `processQueue(false)`，可随离线岗位产料逐步支付并出兵；训练本身按全速推进，资源生产用离线系数。 |
| 自动补兵 | `AutoInfo.autoArmy` 约 1,265,271 为配置；`autoArmy()` 约 1,296,624 按目标数减去现役和待训数，整笔缺额与全军上限合格才调用 `addAmryAmountAuto`。检到的调用点在败北结算约 2,389,247 和胜利结算约 2,390,527；自动下单仍须立即付清，材料不足不建队。离线入口不调用自动补兵。 | 当前无此自动下单；玩家可手工预排队，离线缺料时待训人数保留并在材料足够后继续。 |

这解释了 [P349](wild-offline-queue-p349.md) 的“预排 379 人、4 小时只产 56 人”和 [P350](wild-material-strategy-p350.md) 的材料准备结果为何不能直接当作参考游戏的离线队列行为。参考游戏的预付训练能避免“已下单却缺料停工”，但**不能凭空补出训练材料**：P350 只有在线预存原料 2,751 秒、再离线 4 小时才将 379 人全部训练完成，计入准备时间仅比原方案少 46 秒。参考游戏的自动下单只在战斗结算时触发，也不会在离线生产后重试不足的订单。

若后续决定改成参考游戏的预付语义，须单独审查旧 v32 未付款队列：不能把旧订单直接标成已付款，也不能在迁移时无提示裁掉或追扣历史进度。最小兼容方案需要区分旧未付和新已付批次、保存原下单单价以供取消退款、严格校验数量与有限资源、迁移前保留原文、写入失败回滚，并覆盖在线／离线、取消、导入和旧档测试。当前 `math.js` 的 `serializeSave()`、`validateSave()`、`migrateSave()`、`applySaveToS()` 均没有这层账款字段。鉴于 P350 已证明只改付款时点不能解决短会话补兵，下一步先用现有规则真实验证 [P351](beast-market-offline-session-p351.md) 所得地契能否支付住房、出生并形成下一离线窗的有效军备产能，再决定是否立 v33 队列任务。

本项没有运行新的玩家测试；只读核查期间现有 `tests/progression/military_metals.js` 为 23/23、`tests/ie001/run.js` 为 96/96（均退出 0）。参考游戏源码反混淆且部分符号有拼写错误，以上结论限于逐条可定位的调用关系，不把源码中未见的周期自动补兵推断为存在。回退本项只移除本文；未建分支、提交或推送。
