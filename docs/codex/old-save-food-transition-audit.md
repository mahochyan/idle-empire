# 既有存档首次启用“全人口口粮”规则的过渡审计

本文先记录改动前的只读审计，再记录已实施的一次性过渡。工作区分支 `master`，基线 HEAD `406bce4dc86a7d12f442ceebe5143ec9fa6f6e6d`，其他未提交改动均保留。`index.html` 实际脚本顺序仍为 `config.js → levels.js → sprites.js → math.js → garrison.js → technology.js → ui.js`。AGENTS 提到参考快照 `98571e3` 日期为 2026-09-18；本地 `git show` 查得该提交日期 **2026-05-17**，以当前文件为准。

## 实施状态（2026-09-23）

已在 `math.js` 的 `S.offline` 加持久化枚举 `populationFoodRule`，保持 `rts_save` 主键与存档 **v4** 不变。新档写 `'all'`；无标记 v3、已存在 v4 等合法旧档在候选迁移中写 `'legacy-pending'`，有异常标记则拒载保护。首次历史离线窗口复用现有逐秒结算，只将人口口粮基数切回旧岗位分配人数；这次结算与切换 `'all'` 在同一次主档写入中提交。短窗口、关闭离线或缺时间戳时先写切换检查点。`save()` 或 `tick()` 即使先于显式 `settleOffline()` 调用，也会先完成过渡；`save()` 直接返回该次落盘结果，避免再写一次造成动作回滚与主档分叉。待过渡标记优先于旧 `ops` 幂等键。

历史结算或检查点写失败时恢复结算前状态并进入保护；`tick()` 在保护态不推进，`ui.js` 启动时也不创建 tick 定时器。设置页保护卡提供主档原文及迁移前原文（如有）的手动导出。离线报告注明首次历史口粮口径。导入与恢复仍走统一候选迁移，重载后完成同一过渡。未调整其他资源、人口、容量、队列或口粮系数。

**边界**：正常 UI 在加载后同步调用 `settleOffline()`，玩家动作无法插在两者之间。若通过控制台或自写脚本直接调用 `loadSaveAndApply()`，又先篡改 `S.popAlloc` 等状态再调用公开动作，首次历史窗口会看到被篡改后的状态；本次未加入加载状态指纹与控制台篡改隔离。`offlineNetRates()` 在短暂的 pending 阶段预览的是首次历史窗口口径；切换完成后，界面和在线 tick 都按实际人口显示与结算。

## 改动前结论与可复现影响

改动前 `ui.js` 同步执行 `load(); settleOffline();`，再启动一秒 tick。`loadSaveAndApply()` 对 v3 及更早存档先按旧城镇上限和已分配人数生成 `population.current`，写 `rts_save_premigration`、轮转备份、把 v4 候选写回主档，之后 `applySaveToS()`、保留旧 `ts`。`settleOffline()` 随即用这个旧 `ts` 计算最多 24 小时、0.6 倍的离线窗口。改动前 `productionSecond()` 和 `potentialFoodCostSecond()` 都按 `popCurrent() × 0.1` 收粮，不区分存档形成时的规则；旧规则是按 `popAllocTotal()` 收粮。

因此这是**经济语义追溯**，不是 JSON 迁移丢字段。用现有 VM 测试环境调用真实加载与离线入口复现：v3 存档，旧城镇 Lv.2、工人分配 0、粮 10、旧 `ts` 距今一小时；迁移后实际人口 20，`settleOffline()` 仅推进 **8 秒**，粮余约 **0.4**，报告标记断粮。只替换人口口粮计费基数为历史“已分配人数”时，人口口粮为 0，原本不应因为闲置人口而截断该离线窗口。导入与恢复旧文本通过 `inspectSaveText() → migrateSave() → commitSaveData() → reload` 也会在重载后遭遇同一问题（`math.js:878-922; ui.js:933-963`）。

## 最小安全过渡方案

在现有 v4 `S.offline` 中加一个**持久化规则标记**，例如 `populationFoodRule: 'legacy-pending' | 'all'`。新档默认 `'all'`；对缺标记的合法旧档（包括已有 v4）在候选迁移中填 `'legacy-pending'` 并计入 `filled`。已标记的存档不再改写。`serializeSave()`、`applySaveToS()`、`validateSave()`、`migrateSave()` 同时覆盖该字段；存在时只允许这两个枚举值，缺失才按旧档迁移。不要用 `||` 推断标记或粮食、人口、地契、增长钟等数值的默认值；合法 0 必须原样保留。这个可选的 v4 扩展比只依赖 `d.v<4` 更稳妥：已经生成的 v4 旧规则档也需要过渡。若正式决定升为 v5，也仍需独立标记才能区分已存在的 v4 规则状态。

第一次加载有 `'legacy-pending'` 且离线达到门槛时，用现有逐秒结算器、建筑/队列/上限/断粮规则和 24 小时上限结算，仅把**这次离线人口口粮的计费基数**改为 `popAllocTotal()`；在线 `tick()` 和此后所有离线窗口一律使用 `popCurrent()`。可给 `productionSecond()`、`potentialFoodCostSecond()`、`offlineAdvanceSec()` 传明确的口粮基数模式，避免复制一套公式，也避免把旧规则设成全局开关。离线报告注明本次使用“历史口粮口径”。在同一候选状态里改标记为 `'all'`，**只在主档写入成功后**提交内存状态、`_loadedTs` 与幂等凭证。写入失败则完整恢复结算前的 `S` 与待过渡标记，保持旧时间戳，允许安全重试；不能报告成功。

启动时如果离线窗口未达到 120 秒、离线功能关闭、缺时间戳或时钟回拨，不应把 `'legacy-pending'` 带入正常在线运行，否则后续保存/切后台可能把新规则时段再次按旧规则结算。应在**开启 tick 和可写操作之前**原子写入一次“口粮规则切换检查点”（标记 `'all'`、`ts=now`，粮、兵力、人口与资源不动），并给用户明确原因；低于门槛的时间本来就不结算。若这个检查点写入失败，进入存档保护并暂停有副作用的推进，保留原文供手动导出/重试。普通 `save()` 不可在待过渡的历史窗口上先行写档并清标记，否则会丢掉本应先结算的窗口。反过来，过渡完成后的任何成功在线保存都应写 `'all'`，防止旧口径反复生效。

现有迁移写入顺序可沿用：解析/两次校验只作用于独立候选；原始主档先写 `rts_save_premigration`，有效备份必须写成功，最后才能覆盖主档。任何保护副本/备份/主档写失败，都不得应用候选状态或启动首次离线结算。`settleOffline()` 当前写失败会回滚 `S`，但**不会进入保护**，而 `ui.js` 仍启动 tick；过渡期间应补一个失败闸口，避免在线变化叠加到未提交的旧离线窗口。普通自动备份不能改写 `rts_save_premigration`。

导入/恢复必须在预览与提交入口都使用相同迁移校验，保存被覆盖的当前主档，写成功后重载才执行一次旧口径离线并切换。恢复旧备份时注意备份轮转可能挤掉被恢复的原始槽位；如需承诺**源备份原文**也可恢复，应在轮转前为源文本留独立保护副本或保证它仍在槽内，并在存储不足时中止覆盖。现有 `rts_save_premigration` 保存的是被覆盖的当前主档，不能同时充当导入/恢复源文本的保护副本。预览可以显示“待按历史口粮口径结算一次”，避免用户把第一次断粮或收益误当成即时改档。

旧档实际人口/分配大于新聚落容量时，继续保留 `population.current`、`popAlloc` 和 `legacyBonus`；旧窗口按真实旧分配收费，新窗口按真实实际人口收费，不能为降粮耗悄悄裁剪人口。存档 `food=0`、`deed=0`、`population.current=0`、`growthClock=0` 与合法 `ts=0` 均应保留；时间计算已有 `now||Date.now()`、`lastTs||0` 写法，应在过渡改动中避免让合法 0 通过真假值分支改变含义。

## 建议验收用例

1. **旧档首载真实链路**：v3 与“已存在且无标记的 v4”各一份，闲置人口 20、分配 0、粮 10、`ts` 距今一小时。调用 `loadSaveAndApply(); settleOffline()`：首次窗口不因闲置人口截断，主档留下 `'all'`，原文保留在保护副本；再重启并造第二个离线窗口，必须按实际人口扣粮且只结算一次。
2. **旧档有工人**：分配 5、实际 20，首次窗口按 5 人 × 0.1/秒 × 0.6 计人口口粮，第二窗口按 20 人；在线 `tick()` 始终按 20 人。用真实函数和资源结果断言，不能在测试中重写生产公式。
3. **短间隔/关闭/回拨**：小于 120 秒、离线关闭、无 `ts`、`ts` 在未来的旧档，结算不追溯也不保留待过渡标记进入可写运行；检查点失败时不启动正常 tick。`ts=0` 和粮、人口等 0 值单独覆盖。
4. **故障注入**：保护副本、备份 1/2、迁移主档、离线结算主档分别写失败；原主档与原文可恢复，`S`/标记/`_loadedTs`/`ops` 不被半途提交，不发成功提示，修复存储后重试不双算。先写 PRE 后备份失败时允许 PRE 留存，但主档不得变。
5. **导入与恢复**：导入 v3 / 旧 v4、恢复旧备份、重复点击（5 秒幂等）、重载、再次导入同一原文；每次有意覆盖只按来源时间窗口结一次，被覆盖主档和源备份按承诺可恢复。坏档、未来版本、超额人口、资源/地契 0 不得被静默清零或改写。
6. **浏览器冒烟**：实际按 `index.html` 脚本顺序启动，核对首次离线报告的历史口粮说明、刷新后不再出现旧规则报告，保护状态提供原文导出；VM 的 localStorage/DOM 替身不足以替代此项。

新建 `tests/progression/food_transition.js`，用真实迁移、存档、离线、导入、恢复与 tick 函数验证 v3/v4 首窗、第二窗、短窗/关闭/缺时戳检查点、提前 `save()`/`tick()`、旧幂等键、写入故障、合法 0 与超额人口。实施前相关基线：`population.js` 19/19、`economy.js` 11/11、`workers.js` 8/8、`market_bridge.js` 6/6、IE001 96/96，均退出码 0。实施后六组测试依次为 **11/11、19/19、11/11、8/8、6/6、96/96**，退出码均为 0；`node --check` 检查 `math.js`、`ui.js` 与新增测试全部退出 0，`git diff --check` 退出 0（仅有本地 LF→CRLF 提示）。真实浏览器对新增过渡 UI 尚未在本审计任务中冒烟，不把 VM 替身写成浏览器验证。回退路径是保留现有主档、有效备份与迁移前原文；若修改后出现异常，先停止写入并用原文恢复。旧代码可能不认识新字段/版本，不能把“关闭新规则”和“回退旧代码”视为同一种安全回退。
