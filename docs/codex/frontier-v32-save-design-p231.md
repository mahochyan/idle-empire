## 最小 v32 状态契约

新增一个顶层 `S.development`，以稳定的内部键表示区域，不把母本 ID 或显示名称当存档字段。**提案结构**：

```json
{
  "development": {
    "border": {
      "sites": {
        "copper": { "level": 0, "wins": 0 },
        "iron": { "level": 0, "wins": 0 }
      },
      "collection": { "activeSite": null, "elapsedSec": 0, "pending": { "copper": 0, "iron": 0 } }
    },
    "outer": {
      "village": { "wins": 0, "alert": 0 },
      "town": { "wins": 0, "alert": 0 },
      "city": { "wins": 0, "alert": 0 },
      "capital": { "wins": 0, "alert": 0 }
    }
  }
}
```

`level` 表示已获得的永久采集点等级，`wins` 表示该副本实际已结算胜利次数，两者不能混用：重复胜利可能到等级上限，而次数仍增长。外域的 `alert` 是**预留的我方独立难度进度**，数值更新规则待区域配置确定，不沿用主线击败标志或既有材料域 `S.killValues`。`activeSite` 只能是 `null|"copper"|"iron"`，即使两点都归属也只可激活一处；`null` 意味着自动采集停用。`elapsedSec` 只属于当前选中点的周期。切换/取消激活时，剩余秒数是保留、清零还是按点分别保留，必须在动作规则中确定；**默认建议清零并原子保存**，避免反复切换产生额外产出。`pending` 仅为若选择“定时累计、手动领取”时可保存未领取量的兼容槽；自动直入仓方案保持为 0，禁止把它当无限副仓。

验证约束：v32 字段完整且精确（仅允许配置过的点和区域），`level/wins/alert/elapsedSec` 为非负安全整数，`pending` 为有限非负数；合法 **0** 不得被 `||` 缺省替换。运行时通常保持 `elapsedSec` 在当前周期内，但校验不能因以后缩短周期就把旧档判坏；改变已发布周期时须有明确迁移/换算。未配置 ID、NaN、负数、奇异对象与未来版本必须保护原档而非修成新档。历史等级、库存或待领量超过新上限时保留原值并报告冲突，停止新增，不静默裁剪。显示名可采用我方边疆/外域主题，内部键不受改名影响。若后续决定允许多个点各自累积计时，该结构需要另升版本，不可在 v32 中悄悄改 `elapsedSec` 语义。

## v31→v32、导入与回退

1. 新档和 v31 候选档仅在成功校验后，补上上述全零 `development`，版本升 32。原档其他字段原样保留，尤其 `S.defeated`、资源、兵力、队列、`S.killValues` 与合法超仓库存。旧于 v31 的档继续逐版迁移，最后补 v32；v32 保存中不得因缺键自行补零，缺键是坏档。
2. 同步修改 `serializeSave()`、`validateSave()`、`migrateSave()`、`applySaveToS()`、新档默认值与导出/导入/恢复路径；新字段绝不能只存在于运行中的 `S`。沿用 `loadSaveAndApply()` 在独立候选上校验、迁移、复验，迁移前原文写 `rts_save_premigration`，备份与主档写入都成功后才应用到 `S`。任一步失败进入保护，提供原文导出；普通轮转备份不得覆盖迁移前副本。
3. 结算/激活选择/领取动作先记录涉及的完整快照，再保存一次；保存失败恢复全部内存变化（包括等级、次数、警戒、周期、`pending`、资源、兵阵与战斗日志）。关闭发展副本功能仅停入口/计时与发奖，**保留 v32 字段**。直接回退不懂 v32 的旧程序会把档视为未来版；安全回退须使用懂 v32 的功能开关版，或先手动导出并有明确转换流程。直接恢复迁移前 v31 原文会丢失迁移后的进度，不能称无损回滚。

## 在线与离线同源结算接缝

采集点**不应直接加到 `prodRate('copper'/'iron')`**：该速率进入 `productionSecond()` 的岗位加工配方，现有 `metalConsumeMap()` 会对铜/铁岗位计算煤、矿等原料；点位采集不应误扣这些原料。最小实现是为同一模拟秒建立候选 `{res,development}`：先按现有 `productionSecond(ratio,...)` 结算岗位、军粮与加工，再只对当前 `activeSite` 累计 `elapsedSec`；满配置周期（母本为 60 秒，我方周期需定配置）时，按 `site.level × configuredYield` 生成点位产出，并以与 `creditResourceReward()` 相同的仓容口径向候选资源入库。只写实得量，不能因仓满在 UI 显示名义奖励，也不能给另一点位同时发放。采集点产出不增加训练兵、不改战斗 HP 或驻军资源逻辑。

在线 `tick()` 和离线 `offlineAdvanceSec()` 调用**同一个**候选秒函数；通过参数显式声明该秒是否允许点位自动采集和点位产出系数。若离线政策最终为“允许”，可先用与现有模拟秒一致的 60 秒周期、当秒产出乘 0.6 的我方适配，再做余额和粮食验算；**这不是已证实的母本离线规则**。若政策为“不允许”，离线既不加金属也不推进采集周期；不能离线推进周期却到前台立刻领到满额。在线战斗时当前 `tick()` 提前返回，采集时钟亦应冻结，除非另有清晰决策。`offlineAdvanceSec()` 断粮时本秒建筑/队列与 `{res,development}` 一起回退，`settleOffline()` 写盘失败则恢复整份 `S` 并保留可重试窗口。满仓时默认建议当前周期到点且实得 0、周期正常归零，绝不无界积累隐藏金属；若选择手动待领，需先确定 `pending` 上限、溢出和领取动作，领取只扣除真正入仓量。

不要给 `productionSecond()` 现有单资源预览悄悄混入不稳定的 60 秒突发收益。UI 可分别显示“当前激活点、等级、下次采集倒计时、单次可得/满仓实得”；若展示折算每秒平均值，应标“平均”，不把它写入岗位净速率。UI 同事正在并行美化，正式实施时再做独立小改动和浏览器冒烟。

## 战斗结算接缝

配置加内部 `kind:'borderSite'|'outerRegion'` 与独立区域键，仍复用现有战斗选阵、真实伤害、战损回写和 `battleEpoch`。开战时把区域键、敌方配置及预期奖励快照到该场 `B`，结算时核对 `S.battleEncounter` 与 `B` 快照；旧回调、导入后残留回调、重复 `endBattle()` 不得给新状态发奖。边疆胜利只按配置给予采集点**等级增量**和独立次数/警戒，不直接发金属；满等级胜利可计胜场但等级实得 0。外域胜利按独立区域进度计次，地契/勋章等资源奖励用 `creditResourceReward()` 的实得量与仓容口径，和等级或警戒的更新同一次保存。战败、逃跑、超时无进度/奖励；可以按现有真实战斗规则回写战损。主线 `S.defeated` 不变化，主线首通奖励不触发。`endBattle()` 当前 special 的“一个主材料”分支不符合采集点实体类型，不能复用为直接资源奖励。共享战斗与驻军函数有变更时还需回归驻军，但发展副本奖励不能走驻军结算。

## 决策与实施顺序

先确定我方副本的点位等级上限与每胜增量、当前点切换时钟、满仓溢出、手动领取是否存在、离线自动采集是否启用及其系数、外域警戒/重复奖励规则；母本 `2/1/60秒` 可作对照，不自动成为我方正式数值。随后按“v32 存档候选迁移与保护测试 → 独立副本类型与真实战斗回滚 → 共同秒推进与在线/离线同源测试 → UI 接线与浏览器冒烟”分小单实施。此顺序保证尚未打通存档安全前不会投放可获得的永久点位。

核对命令：`git status --short`、`git branch --show-current`、`git rev-parse HEAD`、`Get-FileHash ... -Algorithm SHA256`、`rg` 和 `Get-Content` 均退出码 0；一次误用 `rg game docs/analysis-economy.md` 因路径不存在退出码 2，随后改用正确根路径。此任务只写设计报告，**运行测试未运行**。
