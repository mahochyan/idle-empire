# 村民成长骨干方案与首通扩容边界（P101，2026-09-25）

- 对应权威设计：[《策划文档.md》§8.4、§8.9](../../策划文档.md)
- 输入：当前`config.js`、`math.js`、P97零胜场首战前自然新档、P15首通地契静态模型及既有人口路线记录。
- 范围：整理人口增长与容量的现行分工，明确一条可继续推演的成长骨干；不改玩家代码、奖励或存档。

## 先分清“村民增加”和“上限扩张”

当前代码的自然出生条件是：有粮、实际人口低于住房容量，并且在线推进十秒；每个触发段增加基础2人。研究并配置小镇“育”政策后，每个已配置政策位再增加5人／10秒。扩村、扩小镇、扩城市分别增加1、2、4人口容量，付地契；扩建本身不直接生成村民。这个基础出生率与母本人口基准一致，当前成长卡点主要是地契续供、研究开放、容量购买频率，以及玩家是否留下足够住房和粮食。

**开局容量断档的可复算边界：**新档初始人口0、容量4（城市Lv1）、食物300、地契30。若立刻把初始地契用于村庄，Lv0→1→2→3→4的真实单级费用为5、6、7、8，合计26，容量升到8、余4；不扩建时自然出生约20在线秒触及4人，预先扩到8则约40在线秒触及8人。之后村庄Lv4→5需9地契，因此仅靠开局赠送不能继续扩容。当前市场建筑要先研究冶铜术并建成；解锁后按实际兑换率100金币换1地契，小镇／城市扩建也另有科技门。故开局地契耗尽到基础市场可用之间，确实存在扩容续供接缝。这里的秒数是由当前在线tick出生规则推算，包含粮食为正、及时扩建的理想条件，不含玩家操作停顿。

P97真实新档走到第1关时，普通战役胜场仍为0，人口与容量已达102／102；同一道路到达该入口累计3,320,154模拟在线秒。之后打完100关，人口／容量仍是102／102，首通没有直接发村民或住房。这说明当前实现没有把村民硬锁在通关后，但该路线约922小时级、操作密集，也**不能**证明成长已追上母本或满足50小时目标。玩家感觉“要打关才能增员”不代表自然出生函数关闭；更可能的体验门是开局地契耗尽后、冶铜术与市场建筑接手续供之前的扩容接缝。此前有18人口零战斗路线，但也不能代表所有策略或高时代增长。

**当前工作区新档人口路线实跑（P101）**：用真实函数VM、全新`S`、关闭随机驻军的三条独立脚本路由，均无普通关胜场且无注入资源，成功达到18／18。逐级扩建路线于5,096在线秒达标；早期村庄扩到8后，当前脚本第500秒建成基础市场，到第1,851秒才付费扩第一等级小镇，说明研究/资源/购契时点把住房空窗拉长。批量扩建不带生育政策路线为6,450秒，带生育政策路线为6,822秒；后者在此路线多研究一个节点并设置一个政策位，抵达18人口反而晚372秒，提示政策本身的每10秒增员收益可能被解锁与资源准备成本抵消，不能只看出生倍率。逐级路线记录56次市场动作、9次单级扩建；批量脚本对市场买卖和扩建操作的统计口径不同，不直接跨脚本比较总操作数。旧P09路径的4,108秒、P08路径的4,275秒是另一组顺序，也不能与本次当成只差一个变量的A/B。该结果是脚本可行样本，不是玩家时长或策略胜率；完整资源与里程碑输出见[人口路线P101原始数据](reports/data/p101-population-routes-0-18.json)，可复跑脚本为[逐级扩建探针](../../tools/verify/probe-population-early-18.js)和[批量扩建／育政策探针](../../tools/verify/probe-population-batch-18.js)。

## 对首通扩容候选的校准

现有P15静态候选是普通关首胜按章节增加拓居地契，Boss再给额外5；100关共600地契，不重复领取。模型用当前真实`settlementCostAt()`计算：若奖励全部投进村庄，百关容量为35；假设小镇、城市科技已开放并把每章资源都投入最优聚落组合，乐观上界为55。第3关另加6地契的早期敏感度能把首次扩容提前到第3关，但百关纯村庄容量仍是35。这说明该候选适合当作**战斗扩容加速**，不足以独立承担全时代劳动力供给；“三类聚落上界”也不是已验证可执行路线。

**战后首通奖励的真实战斗边界复测**：从同一条零关卡胜场的18/18经济路由出发，先按真实建造、训练和编队准备部队；固定随机值0.5，分别运行不发奖、P15当前候选、以及“第3关额外+6”三支独立分支。三支均胜第1–5关并败于第6关；胜负、逐关出战数及战后兵力完全一致。当前候选到第5关累计5地契，仍未扩容；敏感度分支在第3关胜利结算后累计9地契，真实支付9地契扩村，容量18→19，再在线10秒自然出生第19人并由真实动作分配为木工（当前+3木／秒）。这证实奖励必须战后发放，只提前了下一阶段的劳动力/产能，不能回填当前关战力；它**没有**打通第6关战力墙，也不证明第3关+6应定稿。这里沿用固定的后续招募与战斗顺序，没有给新增木工更长时间去积累资源和训练援军，因此不能推断额外劳动力永远不会改变后续战斗。全程把测试奖励留在隔离VM，玩家结算与存档没有改动。胜负及逐关队列见[首通战后扩容反馈边界P101](reports/data/p101-first-clear-battle-feedback.json)，复跑入口为[新档首胜闭环探针](../../tools/verify/probe-population-first-clear-feedback.js)。

## 推荐的成长骨干

1. **自然增员作硬保底。**不打关也能通过当前初始地契、已开放市场和生产积累来扩容量；有粮、住房有空位时自然出生。保留当前基础+2／10秒与已配置“育”的+5／位／10秒，暂不凭单条晚期路线修改人口速度。
2. **首通只加速未来住房。**首次胜利后发放现有地契资源或主题化的“开拓凭证／拓居令”候选，用于真实购买聚落扩建；不直接增加实际人口，不在当前关战斗开始前到账，也不重复首通领取。Boss可作更大的后续扩容节点，但奖励数应按下一阶段岗位预算与真实扩建费校准。
3. **按可工作的岗位定容量里程碑。**当前岗位模型给出的下一项早期验收候选是容量14、实际人口14：可同时安排木、石、两名粮工、学者、铜铁生产和铸币，并保留3名调岗空位；这是我方配方下的工作容量候选，不是母本要求或运行时代门。后续时代容量由必要岗位、原料净流量、研究投入、军粮和备用岗位合算，不用“第几关应有多少人”的任意序列代替。
4. **奖励曲线要用里程碑预算反推。**先确定每个时代第一批必须同时运行的岗位与容量、对应章节入口和可接受等待，再反算首通地契按关／章／Boss怎样分配；市场仍负责零战斗续供。若候选奖励无法让军事路线提前一个容量节点，就调整奖励份额或章节时点，而不是让胜场直接生人。
5. **命名归我方主题。**早期聚落奖励可以用“开拓凭证”或“拓居令”等帝国/工造语汇；保留现有`deed`内部键与兼容字段。电力后才逐步加入我方西幻意象，不把母本源名直接抄作显示名。

## 结论与下一步验收

推荐采用“自然出生保底＋市场/生产提供无战斗扩容＋首通一次性加速住房”的三段式。它解决的是玩家不该被战斗永久锁人口；首通奖励不能替代资源产能或市场供给，也不应成为战力雪球。P15的600地契和第3关+6敏感度继续标为候选，不批准进入玩家运行配置。

下一步应把上述容量里程碑接到同一份新档，至少比较零战斗经济、均衡战斗、科研优先、短时上线／离线四条路线；逐关记录首通收入与重复收入、地契库存和市场兑换、住房容量、实际人口、闲置工人、岗位净产、粮食、军队维护、损兵补回与首次达到下一岗位预算的时点。首通奖领取与扩建须在胜利之后，下一关战力只能使用此前已有的人口和军队。还要对“第3关奖励多出的劳动力”单独留出经济生产和真实补训时间，再与不发奖支线重放后续战斗；目前的10秒固定准备回放不足以回答它能否缩短下一战力墙。P100证明扩仓也会回收部分物资奖励，后续需要把仓储投资纳入同一条经济账，不能将奖励溢出当作人口来源。

本批仅新增设计报告；没有改`rts_save`、游戏运行代码、CFG数值或奖励，也没有把静态容量模型说成自然可达路线。P15模型运行退出码0；它不含出生、市场、战斗、仓容或短时上线模拟，仍须由多策略真实动作回放校准。
